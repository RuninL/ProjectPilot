# Desktop reminders implementation notes

The desktop layer uses the official `tauri-plugin-notification` Rust plugin and the `@tauri-apps/plugin-notification` guest binding. The capability grants `notification:default`; the Settings screen checks/request permission before any native toast is sent. Settings, companion view, geometry and the bounded delivery ledger are validated `desktop.reminders.v1` / `desktop.reminder-deliveries.v1` values in the existing `appsettings` table. JSON export/import/replace and the existing backup flow already round-trip appsettings, so no migration or backup whitelist change is required.

Reminder identity combines entity type, stable entity or recurrence rule/date identity, reminder kind, and scheduled timestamp. Expected and materialized recurrence entries therefore share an identity. Candidate helpers calculate timed meetings, date-only meeting summary entries, task/project/milestone lead dates, overdue summary and daily summary in `Asia/Hong_Kong`; they deduplicate repeated scans, group same-minute delivery, apply quiet hours and pause state, and persist the last 500 delivery identities across restart.

The coordinator is intentionally process-scoped and low frequency. It runs no UI-owned core timer and exposes refresh/stop hooks. A production Windows validation must confirm background scheduling after tray hide and sleep/time-change behavior.

Companion uses a separate `companion` WebviewWindow and rendering entry, with Today and compact Calendar views. It reads through services/repositories, completes tasks through task service, restores a safe appsettings-backed geometry, and uses a lightweight Tauri invalidation event; event payloads only name changed domains and receivers re-read SQLite. Its “Open main” action only emits the fixed internal `dashboard` target, never an external URL.
